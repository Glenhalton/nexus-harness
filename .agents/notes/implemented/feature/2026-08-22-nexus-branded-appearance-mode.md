# Agent Note: Nexus branded appearance mode

Status: implemented

English | [中文](2026-08-22-nexus-branded-appearance-mode.zh.md)

## Problem

Nexus brand occupants (see [the sibling note](2026-08-22-nexus-brand-occupants.md)) put a Nexus logo on the sidebar and hero, but the product's color scheme stayed DeepSeek Harness's own — `ThemeRuntime` (`packages/client/ui-theme/src/client/index.ts`) only ever recognized `light`/`dark`/`system` as preferences, and both built-in `ThemeDefinition`s ship empty `tokens` because their full palette lives in `design-platform.css`'s static/alias CSS blocks. A Nexus-composed build had a Nexus mark sitting on an otherwise unbranded (DeepSeek-blue-accented) dark theme.

## Decision

`nexus` is a fourth built-in preference (`THEME_PREFERENCES` in `packages/client/ui-theme/src/theme-settings.ts`, which `ThemePreference`, `ThemeSettingsSchema`, and `isThemePreference` all derive from) and a third `BUILTIN_THEMES` entry in `ThemeRuntime` (`packages/client/ui-theme/src/client/index.ts`): `{ id: 'nexus', colorScheme: 'dark', tokens: NEXUS_ACCENT_TOKENS }`.

`ThemeDefinition.colorScheme` is a hard `'light' | 'dark'` literal — there is no third rendering mode, and reproducing dark mode's ~78 alias + 73 static tokens as a parallel CSS block for one color difference would be needless duplication. The existing `tokens: ThemeTokens` field is exactly the layering primitive `overrideTokens` already uses for dynamic per-package overrides (`ThemeRuntime.composeActive` folds them in; `ThemePresenter.apply`, `packages/client/ui-layout/src/client/theme-presenter.ts`, applies the composed result as inline `body.style` properties) — reusing it for a permanent built-in required no new mechanism.

The override values are `nexus-homepage`'s own palette (`--mint: #34d399`, documented there as "one accent that means alive"), not an invented color — `rgb(52, 211, 153)` and a deepened `rgb(28, 168, 122)` for hover/pressed states. Reading `design-platform.css`'s dark alias block (`body[data-ds-dark-theme] {...}`) showed DeepSeek's brand blue surfaces narrowly in dark mode: `--dsw-alias-brand-primary` (currently near-white, a monochrome primary CTA; `--dsw-alias-button-primary-fill` derives from it via `var()` and inherits an override for free through the cascade), `--dsw-alias-button-primary-hover` (a literal value, not derived — needs its own override), `--dsw-alias-button-info-fill`/`-hover` (currently the `deepseek-*` ramp), and `--dsw-alias-state-business-primary`/`-tertiary` (same ramp). `NEXUS_ACCENT_TOKENS` overrides these to the mint accent (`rgba(52, 211, 153, 0.16)` for the tertiary business tint, matching `nexus-homepage`'s own translucent `--mintbg` convention) — but stopping there left the theme visually indistinguishable from `dark` on any screen without a visible button or badge, since those surfaces are the only place `dark` itself carries any color at all. A seventh override, `--dsw-specific-sidebar-nav-item-active-accent` (`rgba(52, 211, 153, 0.14)`), fixes that: `dark` sets this token to a plain neutral (`--dsw-static-neutral-bluish-800`, no color), so overriding it puts a visible mint tint behind the active sidebar navigation item — a surface every session shows, unlike a business badge or an info button a given view may never render. Every other alias token (backgrounds, borders, neutrals, bubbles, markdown, scrollbar, error/success/warn states) is untouched, so `nexus` reads as "dark, but every brand surface is Nexus mint instead of DeepSeek blue, and the active nav item now carries color at all."

`boot-theme.ts`'s pre-hydration inline script (`bootThemeScript`) now resolves `nexus` to the dark branch (`preference === 'dark' || preference === 'nexus' || systemDark`) so `color-scheme`/`data-ds-dark-theme` are correct before the shell paints. It does **not** inline the six accent-token overrides — those apply only once `ThemePresenter` runs after the client plugin tree boots, since `light`/`dark` never needed token injection in the boot script (both ship `tokens: {}`) and threading a token map into the inline script for one theme was judged not worth the added complexity for a cosmetic, sub-second flash of default dark-mode accent colors on first paint.

The fourth `AppearanceRow.tsx` cube reuses the existing `IconSparkle16` (`packages/client/ui-primitives/src/icons/index.tsx`) rather than a new hand-drawn glyph or `NexusBrandMark`. Every other appearance-row icon is an exact Figma-extracted fill-geometry shape with a documented frame-id source comment — there is no Figma source for a "Nexus" glyph to extract yet, so hand-approximating one would break that provenance convention. `NexusBrandMark` (`packages/client/ui-brand-nexus/src/client/Brand.tsx`) was deliberately not imported either: that package is a composition-swappable brand occupant (only one of `ui-brand-nexus`/`ui-brand-official`, or neither, is ever mounted per the sibling note), and `ui-theme` taking a static dependency on one specific swappable brand package would break the moment a composition swaps brand packages or mounts none.

## Alternatives considered

**Give `nexus` its own full static/alias CSS block (a third `body[data-ds-...]` selector) instead of a token override.** Rejected: `ThemeDefinition.colorScheme`'s two-value literal type and `ThemePresenter`'s `data-ds-dark-theme` toggle are load-bearing across the whole styling system (`base.css`, `scrollbar.css`, `gradient-shadow-text.css`, `shiki.css` all key off the same attribute); introducing a third selector would require touching every one of those sheets for zero visual benefit, since Nexus's only actual difference from Dark is six accent tokens.

**Solve the pre-hydration accent flash by threading `NEXUS_ACCENT_TOKENS` into `boot-theme.ts`'s inline script.** Deferred, not rejected outright: technically straightforward (the same flat token map, written as inline `body.style` properties in the generated script), but adds inline-script size and a second place the token values must stay in sync for a limitation this note explicitly accepts as cosmetic. Revisit if it proves visually bothersome in practice.

**Use `NexusBrandMark` as the fourth cube's icon.** Rejected: see the coupling argument above — the whole point of `ui-brand-nexus`/`ui-brand-official` being separate, swappable packages is that neither is a hard dependency of core UI packages like `ui-theme`.

## Consequences

A Nexus-composed build can now select "Nexus" as its appearance and get both the brand mark (sidebar/hero, from the sibling note) and a matching accent color throughout the product, not just a logo on an unbranded dark theme. `THEME_PREFERENCES` gaining a fourth value is purely additive to the durable settings schema — no migration needed, existing `light`/`dark`/`system` documents remain valid. The accepted pre-hydration flash (§ Decision) is the one known rough edge; it affects only first paint before the client plugin tree finishes booting, and only for the `nexus` preference specifically.
